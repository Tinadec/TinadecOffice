## 1. 整体架构与策略
TinadecOffice 采用「三层错误处理」模式：
- Core（.NET/MAF）：在 Endpoint 层使用 try/catch 捕获具体异常，映射为带 code/message 的 JSON 响应体。
- Gateway（Bun/Elysia）：作为 BFF，对上游 Core 和 Tool Runtime 的请求进行统一包装，将网络不可达、非 JSON 响应等转化为标准 `{ status, data: { code, message } }` 结构。
- Desktop（Electron/Vue）：通过 `request()` 封装 fetch，统一把后端错误提升为前端 Error，并支持从 `message` 或 `error.message` 提取用户可读信息。

该设计确保跨语言（C# / TypeScript / F#）的错误在 HTTP 边界上保持统一的 JSON 契约，便于上层 UI 一致展示。

## 2. 关键文件与位置
- `.NET Core API 端点异常映射`
  - `TinadecCore.Api/Endpoints/StorageEndpoints.cs`：在每个 MapPost/MapGet 中用 try/catch 捕获 `ArgumentException`、`KeyNotFoundException`、`InvalidOperationException`，返回 `Results.BadRequest/NotFound/Conflict`，响应体包含 `{ code, message }`。
  - `TinadecCore/Lifecycle/StorageLifecycleService.cs`、`TinadecCore/Memory/ProjectSessionStore.cs`：业务层抛出 `ArgumentException`、`KeyNotFoundException`、`InvalidOperationException`、`JsonException`，由端点捕获并转为 HTTP 状态码。
- `Gateway 认证与错误响应`
  - `TinadecGateway/src/auth.ts`：`authenticate()` 返回 `AuthResult { ok, context?, error?: { code, message } }`，错误码包括 `AUTH_INVALID_TOKEN`、`AUTH_INVALID_API_KEY`、`AUTH_REQUIRED`。
  - `TinadecGateway/src/index.ts`：Elysia 中间件在认证失败时设置 `set.status = 401` 并返回 `{ code, message }`；所有路由通过 `setStatus(set, result.status)` 透传上游状态码。
- `Gateway 到 Tool Runtime 的客户端封装`
  - `TinadecGateway/src/toolRuntimeClient.ts`：`proxyToolRuntimeJson()` 捕获网络异常和非 JSON 响应，返回 `{ status: 502, data: { code: 'TOOL_RUNTIME_UNREACHABLE' | 'TOOL_RUNTIME_INVALID_RESPONSE', message } }`。
  - `TinadecGateway/src/coreClient.ts`：类似地代理 Core 请求，统一错误包装。
- `Desktop 前端 API 封装`
  - `apps/desktop/src/api.ts`：`request<T>()` 统一处理 fetch 失败、JSON 解析失败、HTTP 非 2xx，抛出 `Error`，并通过 `extractErrorMessage()` 优先取 `data.message` 或 `data.error.message`。

## 3. 架构与约定
- **异常 → HTTP 状态码映射**：.NET 端点根据异常类型选择 400/404/409，避免 500 泄露内部细节。
- **结构化错误体**：所有错误响应遵循 `{ code: string, message: string }` 格式，code 使用大写下划线命名（如 `INVALID_PROJECT`、`PROJECT_NOT_FOUND`、`AUTH_INVALID_TOKEN`、`APPROVAL_DENIED`、`CODE_TOOL_NOT_FOUND`、`TOOL_RUNTIME_UNREACHABLE`）。
- **网关统一包装**：Gateway 不直接处理业务异常，而是将上游错误原样转发，并在自身网络层失败时注入固定 code（`TOOL_RUNTIME_UNREACHABLE`、`TOOL_RUNTIME_INVALID_RESPONSE`）。
- **前端统一提升**：桌面端将所有后端错误提升为 JavaScript `Error`，调用方可通过 try/catch 捕获并展示给用户。
- **无全局异常中间件**：未发现 ASP.NET Core 的 `UseExceptionHandler` 或 Elysia 的 `onError` 全局处理器，错误处理分散在各端点/客户端封装中。

## 4. 约定与约束
- .NET 端点必须使用 try/catch 捕获已知异常并返回带 code/message 的 JSON，禁止让未处理异常冒泡成 500。
- Gateway 认证失败必须返回 401 + `{ code, message }`，且 code 使用预定义常量（`AUTH_INVALID_TOKEN`、`AUTH_INVALID_API_KEY`、`AUTH_REQUIRED`）。
- 对下游服务（Core/Tool Runtime）的调用必须通过 `proxyJson`/`proxyToolRuntimeJson` 等封装函数，确保网络错误被转换为 502 + 标准错误体。
- 前端 `request()` 是唯一的 HTTP 入口，禁止绕过它直接使用 fetch，以保证错误统一提升。
- 审批门控（approval gate）拒绝时必须返回 403 + `APPROVAL_DENIED`，需要二次确认时返回特定状态码与确认表单数据。

## 5. 缺失与改进空间
- 缺少统一的错误码枚举/常量集中管理，code 字符串散落在各文件中，易产生不一致。
- 未实现全局异常中间件（ASP.NET Core 的 `UseExceptionHandler`、Elysia 的 `onError`），依赖每个端点手动 catch，存在遗漏风险。
- 日志记录未见结构化错误日志框架（如 Serilog/NLog 配置），难以追踪错误上下文。
