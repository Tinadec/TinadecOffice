## 结论与范围

复查基线为 `f67ce4f`，后续修复提交为 `9eb2815`、`fd9e01c`、`651f5fe`、`3e44ef6`（`Everything-changed`）。本文依据当前源码、重新运行的测试及隔离 SQLite 探针，不继承历史对话中的“全绿”“已完成”标签。

## 已确认的问题

### F1：动态派出的执行者丢失自己的提示词（P1，已修）

`FormalModeResolver.ResolveSpawnableTemplatesAsync` 只把角色、工具、能力、资源 grant 和描述转为模板；`FrozenSpawnableTemplate` 没有 `SystemPrompt` 字段。`FullDuplexRunEngine.SpawnableDefinition` 创建的执行定义也未填写它，保持空字符串。`PromptAssembler` 仅在请求中的系统提示词非空时加入该段，不会按版本 id 再补读。

这一问题已修复：模板现在冻结 `SystemPrompt`，动态 worker definition 从模板恢复该提示词，并用选人测试钉住。旧冻结 body 缺字段时按空提示词兼容，不读可变的当前版本。

证据：`TinadecCore/Runtime/FormalModeResolver.cs:367`、`DmaEA/FrozenRunConfiguration.cs:214`、`DmaEA/FullDuplexRunEngine.cs:2449`、`Prompts/PromptsModuleRegistrar.cs:79`。反射探针得到 `system_prompt_empty=true`、`template_can_carry_system_prompt=false`，职责描述仍在。

修复验收：给不同模板配置互不相同的哨兵提示词，通过真实冻结→派发→模型输入链路断言各自只收到自己的指令；提示词版本及模型策略须随冻结快照保持一致。

### F2：派发闸只约束顶层，未按实际调用者下放（P1，已修）

`ComputeDispatchRoster` 仅读取 `ConversationDispatchTargets`。`ToolInvocationScopeResolver` 给所有调用者同一份 run 级 `DispatchRoster`，`task_dispatch` 校验这份名单；选人时再次检查的也是对话身份的名单。执行节点自己的 `AllowedDispatchTargets` 虽已解析，没有成为调用期的派发边界。动态模板连这份关系配置也没有携带。

这不能满足“下层按自己的职责文件按需派发，但权限逐级收窄”。现在 agent instance definition 保存冻结目标包络，`task_dispatch` 在调用期把 run 名册按当前调用者的目标列表再收窄；动态模板也保存可选目标列表。**委派权限上限与直接调用工具的权限仍是不同字段**，不能把子工具集简单当作协调者的直接工具集。

证据：`DmaEA/FullDuplexRunEngine.cs:2693`、`:2706`、`:2535`，`Tools/ToolInvocationScopeResolver.cs:128`，`Tools/ToolDispatcher.cs:901`。

修复验收：顶层允许 A/B/C，执行者 A 只允许 B 时，A 派 C 在调用当下拒绝；A→B→C 每一层均按有效委派包络检查；恢复与重放仍使用冻结关系。

### F3：执行层真并行与执行子 run（部分修复）

引擎现在对没有未完成工具调用的就绪工具任务创建私有 checkpoint 快照并发推进，再由 owner 合并任务节点；已有工具调用/恢复和审批等待仍走串行路径。执行子 run、父子 run 可视化及独立取消/恢复尚未实现。

证据：`DmaEA/FullDuplexRunEngine.cs` 的 `ExecuteParallelToolTaskAsync` / `MergeParallelTaskCheckpoint`。当前 `task_dispatch` 仍向原 run 加任务，不是创建执行子 run；拓扑 DTO 也没有父子 run 字段。

工具链还有两道串行限制：Core 的 `ToolDispatcher.cs:830` 默认用工作区根的互斥锁包住变更调用；`TinadecTools/Runtime/ToolDispatchLoop.cs:85` 在每个工具进程内用一个全局 `MutatingGate` 串行化所有变更工具，shell 也被标为变更工具。因此删掉 shell 的资源租约，并不等于实际命令已能并发；只改引擎或关闭 Core 的序列化开关也不够。并发验收必须穿过真实工具执行路径，并按已隔离的执行目标管理资源。

修复验收：两个独立、带工具的任务用屏障证明同时进入执行；其中一个停在审批时另一个继续；父子容器分别恢复、取消、计费；派发边不能替代可见、通讯、依赖和资源占用边。

### F4：同一 run 的兄弟任务能取得重叠写入范围（P1，已修）

账本冲突判定现在在调用者提供任务 id 时只豁免同一任务重入；同 run 的不同任务仍是独立写入者。旧的 run-only probe API 保留“同 run 视为同一观察者”的语义。

证据：`Abstractions/Ports/IResourceLeaseService.cs:270`。这不是两个 run 的冲突测试能覆盖的。

修复验收：同任务重入仍幂等；父协调者的必要管理租约可显式授权子任务使用；没有该授权的兄弟写任务必须冲突。不能直接把所有同 run 的调用都视为不同持有者，否则同任务工具重入也会被误挡。

### F5：唤醒重试丢失输入，崩溃后不能恢复（P1，已修）

现在领取时把来源移入 `ClaimedSourceMessageIdsJson`，成功才清空；模型失败、取消和过期 claim 会合并回待处理来源。`ClaimToken` 与 `ClaimedAtUnixMs` 负责 fencing 和崩溃回收。新增回归覆盖模型失败重试和旧 claim 回收。

领取查询只接受 pending，没有 running 超时回收、领取者 fencing 或启动恢复。模拟两小时前的 running 行仍有消息来源，排空后它继续 running。正常取消时的 `ReleaseWakeAsync` 不覆盖进程崩溃，而且同样不能恢复已移出的输入。

证据：`TinaChatService.Wakes.cs:110`、`:145`、`:244`、`:349`。

修复验收：在事务中区分待处理与本次领取的来源，成功后才 ACK；失败、取消和崩溃均能重放。领取要有所有者、期限与 fencing，迟到旧执行者不能结算新领取。发帖副作用使用稳定幂等键，允许至少一次处理，禁止“领取即算消费”。

### F6：高峰期来源截断造成静默丢提醒（P1，已修）

来源合并不再使用 32 条截断；领取快照与新到来源分离，来源完整保留。模型上下文预算和后续按游标拆分仍是规模优化项，但不会再静默删除来源。

证据：`TinaChatService.Wakes.cs:13`、`:383`。另外，同一治理成员在不同房间有不同 wake，可以同时进入模型回合；同一个成员的独立上下文尚无单写者或版本合并约束。

修复验收：一次投递 100 条不同提醒，每条最终被消费或明确合并为可回查的事实；同一成员跨房间提醒不能无记录地并发改自己的状态，不同成员仍可并发。

### F7：`own` 可见性仍漏出其他 run 的租约（P1，已修）

`SessionTopologyService.GetAsync` 现在在 `RunId` 过滤存在时同时过滤租约和执行成员，再交给 graph projection；模型侧 `graph_view` 继续通过设置 RunId 收窄。

探针查询 run A，返回了 run B 的一条租约，包括资源路径和持有者信息。这是可见性边界不完整，不是跨租户泄漏的证明。

证据：`Runtime/SessionTopologyService.cs:56`、`:67`、`:73`，`Abstractions/Ports/SessionTopologyProjection.cs:48`。

修复验收：两条 run 配不同任务、租约与实例；受限执行者的 graph/recall/通知不包含另一条 run 的内部事实；组织的公开通讯录可另保留，但不能借成员的 `CurrentRunId` 泄漏内部执行信息。限制必须在服务返回数据时完成，不能只让界面隐藏。

### F8：兄弟通讯目前依赖主动拉取，不能保证及时处理（P1，执行者入口已修）

`org_send` 可将消息持久化。现在执行者也会被点名入 durable wake；Runtime 的 `ExecutorMessageWakeSink` 读取授权消息摘要，写入该 agent instance 的 run-scoped supplement patch 并重新排入原 run。执行者尚未有持久的专用 mailbox turn，也没有自动回复兄弟节点的完整状态协议；它在下一安全边界看到消息。

证据：`TinaChatService.Wakes.cs:39`；`TinaChatMemberTurnRunner` 仅承接常驻治理回合。这不是“没有通讯工具”，而是消费侧未闭环。

修复验收：给正在执行或等待子任务的执行者投递 TinaChat 消息，其下一安全边界可以看到并回应；支持离线成员的待办与终态规则。当前已完成投递和上下文注入，回复和离线策略仍是 N5。

### F9：审批候选窗口可使后续请求饥饿（P1，已修）

`ApprovalGateService.CandidatesAsync` 现在按 approval id 稳定游标分页，跨页后再读取 gate 状态，已终止的前缀不会挡住后续候选。

2026-10-02 纠正：此前的完成判断只是源码推导，记录构造投影后的 OrderBy 实际不能被 EF 翻译，导致后台服务每轮都失败。现将排序移到实体列后再投影，真实 SQLite 空库和 513 个审批跨页测试均通过（`ApprovalGateServiceTests`）；这不是大规模压力或多宿主验收。

修复验收：513 个以上 pending 审批，前 512 个已交人处理时，后面的可推进审批仍能被领取；跨 run/组织公平，分页和游标不反复停在窗口前部。

### F10：常驻治理角色还不是完整的治理执行节点（P2/能力缺口）

`TinaChatMemberTurnRunner` 只承接组织工具、graph 与 recall。每轮新建 messages，没有持久化的成员对话/状态；轮数有限，但响应 `Usage` 没有汇入 run checkpoint 的 `ModelUsage`，事件只记轮数和调用数。报告的提议动作保存下来后，没有一个通用的授权执行器据此暂停、改派或分配执行环境。

证据：`DmaEA/TinaChatMemberTurnRunner.cs:49`、`:88`、`:248`。独立审批门已实现，不代表“审查角色能治理全部执行者”的目标全部实现。

修复验收：成员有独立且可恢复的上下文；治理动词走既有权限与审计路径；回合与审批成本纳入组织/根运行的 token、费用与配额；用户能配置角色和委派策略。

### F11：资源管理目前以登记为主，shell 隔离部分已接（P1/P2）

`environment_acquire` 返回连接描述和空位租约，后续执行请求并未绑定这个环境；worktree 创建后的 assignment 也归创建者 run，没有完整的委派、工作区 rebinding 和合并验收协议。因而“拿到环境”不能证明 shell、浏览器或测试在那里执行。

`ShellTool.HandleShellAsync` 的一次性命令现在走 `CommandSandboxRuntime`；没有流式沙箱后端时 `long_lived` 明确拒绝，不再直接 `Process.Start`。`command_run` 与一次性 shell 共用平台沙箱抽象。Windows 管理员实机、Linux/macOS 后端和长驻流式沙箱仍未验收/实现。

修复验收：分配资源后，冻结的工作区、路径 grant、命令 cwd、工具 provider 与实际执行目标一致；权限只能按委派策略变化。一次性 shell 接平台无关沙箱入口，保留输出流、超时和取消；不支持平台显式拒绝或按用户明确选择处理。长驻终端的策略单独定义。

### F12：规模边界和状态文档仍有误报（P2）

拓扑先加载全部 runs/leases 再截断，环境列表也读取全部活跃租约；组织视图有固定 200 成员/100 房间的上限但没有完整的续页机制。项目 overview 逐会话查询全部未终态 run，未给整体 run/lease 列表分页。尚无数百智能体、多宿主、跨工作区公平性压测。

资源路径统一转小写，Linux 大小写敏感路径与符号链接/路径别名需要平台语义验证。硬插入信号是进程内机制，跨宿主会退化，不能当作集群硬插入已完成。

三份文档中若干“已补”“已完成”只是小切片验收。E4 仍为读模型，R4 的证据 Content 会截断且没有全文引用，E7 的沙箱与前缀规则界面未交付。历史记录保留，当前状态以本次复查和重开的 todo 为准。
