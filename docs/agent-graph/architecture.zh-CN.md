## 1. 一句话

用户只与**一个共享上下文的治理身份**对话；治理层把整理后的意图转交执行层；每一层都可以按**职责描述文件自由接线**到下层；所有动作在 Core **带电**（每个动词都过权限检查）。

## 2. 命名与术语（本节是后续所有文档的用词基准）

| 概念 | 用词 | 说明 |
|---|---|---|
| 用户默认对话对象 | **对话身份**（conversation identity） | 也就是委员长 / 会议智能体。它是一个**共享上下文 + 一份职责 + 一份权限**，**不是一个实例**。名字（委员长 / 会议 / 规划）由描述文件决定，不写进代码 |
| 两层 | **治理层**（operation）/ **执行层**（execution） | `planning` 只是旧数据的兼容别名，不是第三层 |
| 岗位与实例 | 岗位 = 描述文件；实例 = 临时句柄 `<agent>#<n>` | **名字不重要，职责和权限才重要**。同名实例靠句柄区分 |
| 接线方式 | **拓扑自由**（free topology） | 谁派谁、谁看谁、几个实例、管多宽，由描述文件 + AI 判断决定，引擎不预设 |
| 权限形态 | **权限下放**（delegated authority） | 用户可以选择把权限交给委员长、交给审查智能体、或两者共同 |
| 引擎侧原则 | **动词固定 + 每个动词带电** | 引擎只保证"这件事做得到"和"做这件事一定过检查"，不保证"什么时候该做" |
| 会话在 TinaChat 里的形态 | **组织**（organization） | 一个会话 = 一个组织：成员、通讯录、会议室、私聊、公告板都在组织里，见 §9 |
| 治理角色的观察与判断 | **报告**（report） | 发在会议室里的结构化帖子，只陈述与建议，本身不改变任何状态，见 §9.3 |
| 模式 | **预设模板**（mode） | 一组"谁对话、谁能被派、各持什么工具、提示词怎么写"的组合，见 §12 |

**术语澄清**：早先讨论里说过的"电路自由"作废，正式用词是**拓扑自由 + 权限下放**。

## 3. 三层视图

```
                         ┌─────────────────────────────────────────┐
用户 ──（默认唯一入口）──▶│ 治理层 operation                          │
                         │  对话身份（共享上下文，可多实例并行回话）    │
                         │  审查智能体 · 上下文压缩 · worktree 管家    │
                         │  环境管家 · Git 提交 · 冲突治理             │
                         └───────────────┬─────────────────────────┘
                                         │ 转交：整理后的意图 + 远期计划
                         ┌───────────────▼─────────────────────────┐
                         │ 执行层 execution                          │
                         │  计划智能体 ×N（可再往下派）               │
                         │    └─ 执行智能体 ×N（检索/上网/改代码/浏览器）│
                         └─────────────────────────────────────────┘

通讯底座：TinaChat 组织（一个会话一个组织：通讯录 · 会议室 · 私聊 · 公告板；执行层也是成员）
控制面：  Core 事件流 + 任务图 + run 树（派发 · 结果 · 审批 · 账本）
```

### 3.1 层级是图，不是管道（重要）

从**链条思维**转向**图工程思维**：

- 链条思维：A 派 B，B 派 C，C 派 D —— 一条线，每层只能看到下一层。
- 图工程思维：**谁派谁、谁看谁、谁管谁、谁和谁说话，是四张不同的边**。派发边是单向的，**可见边是向下的全通**，治理边是横向的（审查智能体可以看到所有执行者，包括不在它派发链上的），通讯边是多对多的（通讯录与会议室，见 §9）。

因此：

- **派发**（谁能创建谁）由描述文件与权限包络决定，逐级收窄。
- **可见**（谁能看到谁在干什么）默认**向下全通**：治理层的任何智能体都可以看到下层全部实例的实时状态，**跨 run**。用户可以为某个身份关掉这个能力，但默认是开的。
- **治理**（谁能干预谁）由动词表 + 用户配置的门决定。
- **通讯**（谁能找谁说话）走 TinaChat 组织：通讯录与会议室由成员在运行时自己建立，组织策略给出边界。兄弟节点之间可以直接对话，但**只能经 TinaChat**，不存在旁路。

**五条规则**（判断一个机制是不是"链"的标尺）：

1. **共享的是状态，不是接力。** 想知道什么就按权限去读图，不等别人转告；信息不能只沿派发树经委员长一层层中转。
2. **每个智能体都是常驻节点，有自己的上下文和预算。** 治理角色不在任何执行者的 run 里当"一个步骤"跑，执行者也不必等它。
3. **边由智能体在运行时自己连，前提是有权限。** 描述文件给的是默认边和边界，不是全部的边。
4. **并发写入按状态种类合并，不排队。** 帖子和事件只追加（永不冲突）；计划、目标带版本号（过期写入被拒，重读再写）；只有物理上独占的东西（worktree、环境、终端）才用租约。
5. **run 只是执行容器。** 派发树只是图里的一种边，不是组织本身；图模式画的应是这张图，而不是一棵树。

### 3.2 层级与递归

- **计划智能体不递归**：它已经在执行层，不能再派计划智能体。
- **只有治理层可以往下派计划智能体**（或是派一个直接干活的执行智能体）。
- **执行层怎么处理是它自己描述文件的事**：可以直接派一个执行智能体端到端做完（分析 + 改代码），也可以自己做完不派。引擎不规定。
- **深度由描述文件决定，但必须有硬顶**（引擎计数，见 §8）。

## 4. 用户交互：三种投递

| 模式 | 语义 | 目标 |
|---|---|---|
| **排队 queue** | 等当前这项跑完，再交给智能体 | 不打断，不并发 |
| **插入 insert** | 中途改变正在进行的工作 | 软插入（安全边界生效）/ 硬插入（中断当前模型或工具调用） |
| **并行 parallel** | **在同一个共享上下文里再开一个实例回答用户，前面的任务照旧跑** | 这是我们的差异点 |

**并行的定义（明确）**：并行不是"同一个 run 里塞两个循环"，而是**同一个上下文里多一个实例**。上下文共享，实例各自推进。

参照（同类产品的实物做法，供实现参考）：

- **Codex**：会话级输入队列 + 轮内待处理输入；插入输入在**轮的显式边界**生效；中断是独立操作，而且**队列里还有待处理输入时，中断主动让步**（优先投递，不打断）；中断要与正在执行的任务一起收尾，不是从外面硬杀。转向（steer）只截断模型的输出流，已经开始的工具调用照样等它跑完；中断时交互式进程不杀。
- **DeepSeek Harness**（2026-09-28 核实服务端）：只有 `queue` 与 `steer` 两种输入模式。排队的每条消息各成一个后续回合，在回合边界取用；转向**什么都不打断**，等当前模型回复和它发起的工具调用全部结束，再作为同一回合的下一步；"停止"是单独的取消（部分输出保留并标为中断，进行中的工具等它结束、bash 杀进程）；fork 是把会话日志复制成新会话，之后两边互不共享。
- **Claude Code**：运行中输入的消息排队，当前工具调用结束后在同一回合送达；Esc 立即停止当前工具调用。
- **结论**：三家插话时都不杀正在跑的工具，只有"停止"才中断；**三家都没有"共享同一上下文的并行实例"**——这是我们的差异点。证据与出处见 `docs/research/shell-steer-survey-2026-09-28/README.zh-CN.md`。

## 5. 一条 run 与并行的关系（最重要的结构决定）

**现状事实**：一条 run 的状态是一份单写者 checkpoint；同一个 run 里带工具的子智能体是**逐个执行**的，而且工具循环会停在"等子任务 / 等审批"的位置。

**因此本架构采用**：

> **并行的单位是 run，不是 run 内部的循环。**

- 用户点"并行" → 在同一个会话里开**一条新 run**，共享同一份上下文（带版本号的补丁同步），前面那条 run 不受影响。
- 计划智能体、执行智能体、审查智能体，**各自是一条 run**（各自有租约、checkpoint、预算、审批、可单独恢复）。
- **run 树 = 项目的生命周期树**：谁派了谁、各自状态、各自的产出，直接可以画出来（图模式 / 空间模式的底图）。
- 好处：真并行、可单独恢复、可单独授权、可单独计费；不需要动单写者 checkpoint 那块地基。

**代价（诚实）**：跨 run 的上下文只能通过补丁传播，不是共享内存；写入冲突要显式处理（沿用现有的带版本号校验 + 拒绝/合并）。

## 6. 治理角色

治理层的角色**全部由描述文件定义**，可替换、可新增。下面是我们讨论过的清单，不是写死的枚举：

| 角色 | 职责 | 备注 |
|---|---|---|
| **对话身份**（委员长/会议/规划） | 唯一默认用户入口；整理意图；远期规划；项目生命周期 | 共享上下文，可多实例 |
| **审查智能体** | 独立上下文审批高风险动作；**并负责执行者之间的冲突治理** | 治理层；上下文不得被污染；可见所有 run |
| **上下文压缩** | 把多份下层报告压缩成分层摘要，并做向量存档与回查 | 有独立向量库存档 |
| **worktree 管家** | 创建 / 回收 worktree，指派哪个实例用哪一个 | 与资源账本强绑定 |
| **环境管家** | 测试 / 云端 / 远程 / 本地 / 终端环境的分配与回收 | 与资源账本强绑定 |
| **Git 提交** | 提交边界、分支策略、推送前检查 | 已有雏形（run 结束建议） |
| **冲突治理** | 检测两个执行者触碰同一路径/资源，并给出裁决或上报 | 可与审查智能体合并，也可独立 |

**角色的形态**：治理角色是**会话级的常驻节点**（组织成员），有自己的上下文、预算和工具面；它不在任何执行者的 run 里同步运行，执行者也不用等它。这也是"审查智能体的上下文不被污染"能成立的前提。

**角色的激活方式**：角色在描述文件里声明**订阅哪些事实**（例如"动作待批""路径被两个实例触碰""上下文超预算"）。事实发生时，一条提醒投进它在组织里的收件箱（复用 TinaChat 的唤醒队列：与消息同一事务写入、等待期间合并、限速不丢），它用自己的上下文跑一轮。这不是一张写死的时刻表，见 §8。

**它能做什么**：看（按可见边读图）、说（在会议室发报告，§9.3）、动（只能调用固定动词表里它被授权的动词，每个动词都过 PDP）。第一版先开放"看"和"说"。

## 7. 权限与门

### 7.1 四层权限（从外到内）

1. **资源包络**（resource envelope）：这个实例能读/写哪些路径、能开几个 spawn。收窄只能向下，永不放宽。
2. **工具面**（tool ceiling）：这个岗位能用哪些工具。
3. **审批门**（approval gate）：这个动作要不要人批 / 谁可以批。
4. **治理动词**：治理角色能对下层做哪些干预（停 run、改派、开 worktree、批动作）。

### 7.2 两道门由用户配置

用户三选一：

- **全交给对话身份**：委员长批就行（快，风险高）。
- **全交给审查智能体**：独立上下文批（稳，慢，费 token）。
- **两者共同作用**：委员长先筛，审查智能体再用独立上下文筛第二遍。

**两道门是"与"关系时，必须是两条独立的记录**：各自留下"看了什么、依据什么、结论是什么"。

**已落地（2026-09-29）**：三选一就是三档权限模式，按消息选——`delegate-conversation` / `delegate-reviewer` / `delegate-both`。两条硬边界不随模式变：

- **委托只替人点审批这一下**，不放宽任何绑定检查（请求哈希、冻结清单、实例授权照旧，批准仍只能消费一次）；
- **仅人工工具与高风险调用等人**。推送、删除、外连和 Core 虚拟工具不接受委托规则；`elevated/high/critical` 与未知风险不能交给模型。唯一的工具例外是按具体会话登记的 `shell`/`command_run` 委托，同样只覆盖低/中风险调用，不能越过配置的更窄上限。

审查员看不到对话：它的全部上下文是动作（去密钥的参数）、所服务的任务、客观事实；对话身份的门多看一项用户目标。谁都答不清就退回给人，从不默认放行。实现见实现文档 §6。

### 7.3 治理层可见性

- **默认向下全通**：治理层看得到下层所有 run 的实时状态与事件。
- **对话身份更应如此**：它必须看得到下层治理角色在干什么（包括审查智能体的判断）。
- 用户可以按身份关闭或收窄这个能力。

### 7.4 资源与 shell（2026-09-29 已定）

调研了 Codex、DeepSeek Harness、Claude Code 三家的做法（出处见 `docs/research/shell-steer-survey-2026-09-28/`）：**没有一家给 shell 加锁**，大家靠的是隔离；多个智能体互相冲突的问题三家都没解决。我们的做法：

1. **shell 不按命令加锁。** 命令跑之前没人知道它会写哪些文件，要锁只能锁整个工作区，那就把并行变回了串行。
2. **派发时声明写入范围。** `task_dispatch` 与规划任务带 `write_scope`（路径或 worktree）；两个写任务范围重叠即拒绝，并告诉派发者谁占着——冲突在任何命令执行之前就可见。
3. **要同时改同一块，就分到不同的 worktree。** 由 worktree 管家分配，一个 worktree 同一时间只允许一条写入 run：这才是账本里真正的独占租约。
4. **事后核对。** 用独立的 git 索引拍快照（不碰真实仓库），每个任务结束时比较一次；改动超出声明范围、或两个 worktree 改了同一文件（合并必然冲突），审查智能体在合并前报告。
5. **shell 进沙箱。** 今天 `command_run` 已走 Windows 沙箱后端，`shell` 还是直接起进程；先验证 cmd.exe 在沙箱账户下能正常工作，再切换。
6. **审批加前缀规则**（例如预先允许以 `npm test` 开头的命令）。
7. **shell 默认不进委派审批。** 用户把审批交给审查智能体时，`shell` 仍需人批，除非用户单独勾选。

## 8. 引擎的固定部分（不可由 AI 决定）

这几条是**不变量**，任何模式下都必须成立：

1. **单一事实源**：状态在 Core，事件是唯一的可重放事实流；Gateway 只代理，Desktop 只呈现。
2. **动词带电**：每个治理动词（唤醒、停、改派、审批、开/收资源）都过 PDP；不存在"AI 批准就绕过检查"的路径。
3. **计数不信自觉**：深度、每 run 实例数、并发数、唤醒次数、自动批准次数，**全部由引擎计数并强制**，AI 只能在这些上限内自由决定。
4. **固定的动词表**：引擎只保证一小撮动作做得到、且一定带电。AI 不能发明引擎不会执行的动作。
5. **可追溯**：每个治理动作留下发起者、依据、结果、时间。

> 一句话：**拓扑自由，动词固定，动作带电，计数在引擎。**

## 9. 通讯：TinaChat 与 Core 的分工

| 走哪里 | 承载什么 | 理由 |
|---|---|---|
| **Core 事件流 / 任务图 / run 树** | 派发、等待、结果、审批、账本、run 状态 | 必须结构化、可重放、可审计；是事实源 |
| **TinaChat** | 讨论、广播、公告、人类介入、**进阶用户直连某个智能体** | 通讯语义（谁说了什么、谁该被唤醒） |

**已定原则**：讨论可以"升级"成控制动作（今天的"简报 → 采纳 → 执行"就是这个模式），但**结果的真相源不放在聊天消息里**。

### 9.1 会话 = 组织（2026-09-29 已定）

一个会话在 TinaChat 里是一个**组织**，而不是一间会议室：

- **成员**：用户本人，加上这个会话里的每一个智能体实例——对话身份、治理角色、计划智能体、执行智能体，**执行层也是成员**。每个实例有自己的参与者身份，靠句柄区分（例如 `reviewer#1`、`search#2`）；实例结束后身份保留为离线，已发过的话仍可追溯。
- **通讯录**：谁能找到谁、给谁发消息。默认边从图里来：派发者 ↔ 被派者、同一派发者下的兄弟、治理层 ↔ 所有人；成员可以在运行时自己加联系人（拓扑自由），组织策略决定哪些要对方同意或治理层批准（权限下放）。跨组织（跨会话）默认不通。
- **会议室**：全员大厅、按计划自动建的计划室（一个计划智能体 + 它的执行者 + 旁听的治理层），以及成员自己拉的临时会议室；联系人之间可以**私聊**；**公告板**只有治理层和用户能发，所有成员可读。
- **兄弟节点可以直接对话，但只能经 TinaChat。** 帖子只传递信息；改变状态只能靠动词，动词照样查权限。
- **进阶用户**可以在组织里直接对某个智能体说话；默认入口仍是对话身份。

### 9.2 边界

TinaChat 本身就是 Core 的模块，组织放在上面不违反"Core 是唯一状态源"。守住一条：**帖子是视图和讨论，不是真相**。计划的真相在任务节点上，占用的真相在账本里，帖子引用它们（界面上显示对象的最新状态，而不是一段过期文字）。

### 9.3 报告

**报告是治理智能体对图里某一块的观察和判断，以结构化帖子的形式发在会议室里。** 与其他东西的区别：任务结果是被派的活的产出；报告是对别人的活的观察；事件是机器事实（例如"租约已取得"）；命令会改变状态，而报告本身不改变任何东西。

一份报告包含：作者（身份 + 实例句柄）、关于（指向图里的节点）、类型（冲突 / 风险 / 偏离计划 / 预算 / 进展摘要）、发现、证据（引用事件序号、租约记录、diff，可回查而非复述）、严重度（知会 / 警告 / 阻断）、建议（可附一个"提议动作" = 一个动词加参数）、状态（未处理 / 已执行 / 已驳回 / 已被取代）。

提议动作**不会自动执行**，要由持有那个动词的一方执行；决定时带版本号，过期的决定被拒绝——与今天的"简报 → 决定 → 执行"同一个模式。压缩智能体在这里的活很自然：给对话身份维护会议室摘要，原文存进向量库供回查。

### 9.4 现有底子与缺口

已有：参与者身份、群聊/私聊、每条消息发出时冻结的受众（即持久收件箱）、"简报 → 决定 → 另开 run 执行 → 结果回帖"、与消息同一事务写入的唤醒队列（合并、限速、防重复领取）。

2026-09-29 已补齐（实现见 implementation §14）：组织与会话一一绑定，派出的每个实例自动成为成员；默认通讯录按图推导、额外联系人需对方同意；大厅、计划室、临时会议室、私聊、公告板；报告帖带"关于哪个对象"与提议动作，读取时显示对象的当前状态；常驻治理成员被提醒后用自己的上下文与工具跑一轮，受每小时预算约束；模型可按会议室、按游标、按类型读。

仍缺：组织策略还没有写进模式（"加联系人是否要治理层批准"目前固定为"只要对方同意"）；报告的提议动作还没有对应的引擎动词（今天由持有者用自己的工具执行后记录决定）。

## 12. 模式 = 预设模板

开销与自由度的取舍交给用户：**高度可自定义，同时预设一组模板**。智能体包里的模式就是这些模板——模式之间的区别，是"谁对话、谁能被派、各持什么工具、预算多少、提示词怎么写"这些细微差别的组合。

预设模式用其他智能体产品里熟悉的词命名，让用户不觉得陌生，再在描述里写出我们的特点（种子包 2.12.0）：

| 模式（slug） | 一句话 | 编排档位 |
|---|---|---|
| **Solo**（`solo`） | 亲自动手，活大时派帮手分担 | solo_dispatch |
| **Plan**（`plan`） | 只读调研、写方案请用户确认；确认后同一会话切到 Solo 执行 | solo_dispatch |
| **Team**（`free_director`） | 协调者按需组队，拆给多名执行者再汇总验收 | free_form |
| **Review**（`review`） | 几名评审各自独立、各查一个角度，核实后合并成一份清单 | free_form |
| **Spec**（`spec`） | 需求 → 设计 → 任务三份规格逐份确认，再按清单实现 | free_form |
| **Graph**（`vibe_graph`） | 固定角色沿画好的协作图分工，每条连线写明交付物 | self_dispatch |
| **Workflow**（`fixed_pipeline`） | 按固定阶段推进，不临时加人、不越界 | deterministic |

**对话身份只有一个（E6，种子包 3.0.0）**：七个模式全部由 `meeting` 对话——它就是§2 说的"一个共享上下文"，`meeting` 的智能体定义携带全部工具作为天花板，不需要工具的模式在绑定上把工具逐个关掉（档位从有效工具推导，不从 slug）。模式只改变策略，任何两个模式都能在同一会话里互切。存量会话若冻在旧身份 `solo_master`（不再被任何模式引用，仍随包发布供恢复）上：准入时若会话没有活跃 run，一次性迁移到新身份；有活跃 run 则维持拒绝（那条 run 的名册是按它开始时的身份冻结的）。

## 13. 集群思维（2026-09-29）

一个会话可以有几百个实例、一台机器上可以同时跑很多会话。下面这些是设计时守住的形状，新机制也要照着做：

1. **没有 O(n²) 的存储。** 默认联系人按图在检查时推导，只存经同意的额外边；公告板帖只写发送者一行受众。
2. **写入是 O(被寻址者)，不是 O(成员)。** 会议室帖只冻结"发送者 + 被提及者"的受众，其余人按游标读；报告只把 warning/blocking 送进用户与对话身份的收件箱。
3. **房间有上限，满了分裂而不是拒绝。** 计划室每间 ≤ 64 人，派发者的执行者更多时自动开下一间；大厅只放看全局的角色。
4. **背压用推迟，不用丢弃。** 常驻成员每小时唤醒有上限（每成员、每组织各一道），超了推迟到下一个窗口，来源合并保留；通知按主题 + run + 时间桶去重。
5. **到期判定走索引。** 唤醒队列按 `DueAtUnixMs` 在 SQL 里取到期行，不扫全表；清理按主键分页。
6. **活性回收而不是超时。** 资源租约不设过期时间，持有者 run 终态后由下一个争用者回收——崩溃留下的租约不会永久挡路，也不会在长任务中途被误回收。
7. **所有视图有界并报告截断。** 拓扑、成员、房间、报告、事后核对的路径列表都有上限，并明确告诉读者"被截了"。
8. **排空并行、互不阻塞。** 一次排空里的多个成员回合并行执行；每个回合有自己的上下文与事务。
9. **尽力而为的旁路永远不拖垮主路。** 入组、通知、下线、报告注入都是尽力而为：失败只记日志，run 照常完成。
