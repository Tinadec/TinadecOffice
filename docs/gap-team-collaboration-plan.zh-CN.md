# 计划书⑧：团队协作 — 远期评估书（对应扩张调研 §3.4；含宿主+隧道方案）

> 状态：**评估书** v1（2026-11-03）——按决策"这是未来要做的，先出调研/评估，不出执行批次"。**未登记**，待批准。
> 用户的方向性意见已登记：倾向"用用户本地电脑（做宿主），让其他用户通过隧道连接指定的服务器/客户端"，即**无云厂商、自建/隧道式中继**。本评估书按此方向展开。

## 0. 结论一句话

团队协作的两家对标（Qoder 云端对象模型、Codex 云任务）都建立在"云侧服务端事实+多租户"上，而本仓是本地优先+SQLite 单机。按用户方向，评估的最优解是**宿主模式**：一个用户的本地 Core 当宿主，其他用户经隧道以设备身份接入——它直接复用计划书⑤（远程多机）的全部地基，把"设备互控"多人化；"指定服务器"降级为可选的自建轻中继。

## 1. 对标事实（来自扩张调研，此处只留结论）

- Qoder：`/api/v1/collaboration/*` 完整对象模型（projects/issues/discussions/files/team-profiles/agent-memberships/invitations）+ collab-cli（CLI 不持有长期凭据，身份三态 User/RuntimeOwner/RuntimeAgent）+ squad 智能体团队（Leader/Member、委派监督边界原子转移）+ 企业管控缓存位（`collaboration_governance`）。这是"全量形态"的参照。
- Codex：无人类协作面（多智能体编排模板不算）；云任务走 ChatGPT 账号。
- 共同点：**没有一家做本地 P2P 人类协作**——宿主+隧道方向没有竞品验证过，也没有竞品封死。

## 2. 三个候选形态（评估矩阵）

| 形态 | 说明 | 复用 | 成本/风险 | 评估结论 |
|---|---|---|---|---|
| **A 宿主模式（推荐）** | 一个用户的本地 Core 当宿主；其他用户经隧道+计划书⑤的设备身份接入；对象模型最小化=共享会话目录+会话移交+指派，不建 Qoder 全家桶 | ⑤ 全部（证书身份/准入策略/影子会话/审计）；审批三道防线 | 低-中；新问题=审批权限面（谁批谁的 run）与宿主可用性（宿主机关机=团队停摆） | **推荐起步** |
| B 自建轻中继 | 一台"指定服务器"（VPS）跑极小 rendezvous/信令服务（对标 Qoder Relay 五端点：registration/rendezvous/tickets/inbox/links），只做握手与信令，数据 P2P | Qoder 的降级链设计（Relay 不可用→回落 LAN） | 中；多一份公网运维面+安全审计 | 作为 A 的**可选组件**（跨 NAT 场景），不单独立项 |
| C 无宿主多 Core 同步 | 多个对等 Core 同步状态 | — | 高（CRDT/冲突、审计重组），与"Core 唯一状态权威"原则冲突 | **不做** |

**隧道选项**（用户"通过隧道连接"的具体化）：Tailscale 类组网（零公网暴露，首选）、SSH 隧道（现成，体验一般）、自建 FRP/WireGuard（可控，运维成本）。评估结论：宿主模式下隧道只是**传输选择**，接入身份/准入/审计全部走⑤的体系——隧道不承载授权语义。

## 3. 团队化带来的真问题（立项前必须回答）

1. **审批权限面**：现在的审批模型是"本机用户批本机 run"。宿主模式下谁批谁的 run、能否委托（对标 Qoder RuntimeOwner 的"Issue 绑定的所有者委托"）、审批过期在多用户下升级给谁——这是产品问题，先于技术。
2. **身份**：⑤ 的设备身份是"物的身份"；团队需要"人的身份"。A4（OIDC）延后项在此并入：宿主模式下 OIDC 只需要一个极小实现（宿主验证成员身份即可，不必多租户）。
3. **SQLite 并发**：多人写放大既有 Error 5 抖动族（既有报告 §4.5）——连接生命周期收口是硬前置。
4. **监督边界**：squad 的 `terminal_callback_boundary`（监督义务原子转移）值得抄——团队场景里"谁对这次 run 的结果负责"必须有一等答案。

## 4. 评估触发条件与最小起步（若立项）

- **触发**：≥2 个真实用户出现共同工作需求时立项；不预设时间表。
- **最小起步**：⑤（RM1+RM2）→ 多人准入策略（人×工作区）→ 共享会话目录+移交 → 按需长对象模型（先"指派"，后"讨论"，最后才考虑 issue）。
- **明确不做**（无论何种形态）：云厂商 SaaS 化；对象模型全家桶一步到位；无审批的多用户自动化。

## 5. 与其他计划书的关系

- 直接地基：计划书⑤（设备互控）；前置：A4（OIDC 极小切片）、SQLite 并发收口；对象模型若生长，计划书②（Quest）的任务实体是"指派"的本地雏形。
