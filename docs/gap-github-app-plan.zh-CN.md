# 计划书⑨：GitHub App — 远期评估书（对应扩张调研 §3.5；薄中继+本地执行）

> 状态：**评估书** v1（2026-11-03）——远期方向，不出执行批次。**未登记**，待批准。

## 0. 结论一句话

GitHub App 是计划书⑦（PR 审查本地版）的云扩展形态。若做，形态定为**薄中继+本地执行**：公网小服务（无状态）收 webhook/@mention → 经计划书⑧的隧道/⑤的设备身份转发到用户本地 Core → 本地跑审查（⑦）→ PAT 回帖。云层不碰代码、不存数据——与用户"本地电脑做宿主+隧道"的方向一致。

## 1. 为什么现在只评估、不立项

1. **无竞争压力**：Qoder 0.5.1 一手证据表明对标产品没做 GitHub App（IDE 仅标配 `github-authentication`，桌面 preload github 命中 0）；Codex 做了但形态是云侧重资产（云端沙箱执行），本仓不必对标它的云。
2. **前置未备**：需要公网可达的接收端（云组件）+⑦ 的审查链+⑧/⑤ 的远程触发链——三者都不在。前置链：⑦ 上线 → 用户出现"在 GitHub 上直接 @"的真实需求 → 再立项。
3. 云侧可靠性是已知痛点：Codex 的 @codex 触发在 2026-02/03 有多次可靠性 issue——本地触发链（⑦）反而是本仓的稳定性优势，先用好它。

## 2. 形态评估（立项时的设计边界）

- **薄中继职责**（且仅限）：收 GitHub webhook、验签（X-Hub-Signature）、按 repo→用户映射路由、把"请审查 PR #N"作为一条事件经隧道投给目标用户的本地 Core。不代理代码、不代理 diff、不缓存 PR 内容——数据面始终在 GitHub 与本地之间直连（本地 PAT 拉）。
- **本地执行**：复用⑦ 全链（REST 最小面/review 模式/评审卡）；回帖可二选一：本地 PAT 直发（简单）或经 GitHub App 安装态发（正式，需要 App token 管理）——评估倾向**先 PAT 后 App token**。
- **审批语义**：webhook 触发的只读审查=低危，可走规则审批；**写操作（回帖）永不自动**——即使触发来自 GitHub，发帖确认仍在本机评审卡上完成。
- **安全边界**：公网→本地穿透是新增攻击面；中继只做信令+验签，隧道侧身份/准入全部复用⑤；中继被攻破的最坏结果=「向用户本地 Core 投递一条需本机确认的审查请求」——把这句话写进 security.md 作为设计不变量。

## 3. 触发条件

- 计划书⑦ 上线且通过 live 验收；≥1 个用户提出"在 GitHub 上直接 @"的真实需求；一台可公网部署的"指定服务器"可用（用户方向的既有意见）。
